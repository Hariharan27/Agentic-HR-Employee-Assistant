# Agentic HR & Employee Assistant — Project Specification

## 1. Project Overview

The Agentic HR & Employee Assistant is a single conversational AI service that enables authenticated employees and authorized managers to interact with enterprise HR and workplace services through natural language.

The application demonstrates Agentic AI concepts including:

- Natural-language intent understanding
- Dynamic workflow routing
- Retrieval-Augmented Generation (RAG)
- Tool/function calling
- Multi-step agent workflows
- Conversational context
- Structured data extraction
- Deterministic business-rule execution
- Human-in-the-loop confirmation
- Authentication and authorization
- Transactional database integration
- Multi-domain orchestration

The system provides three primary workflows through one chat interface:

1. Employee HR & Leave Assistant — Primary
2. New Employee Onboarding — Secondary
3. Workplace Parking Assistant — Third

Users do not manually select a workflow. The agent determines the appropriate domain from the conversation and routes the request automatically.

---

# 2. Assessment Objective

The primary goal is to demonstrate an HR Chat Agent capable of:

- Authenticating employees
- Answering questions from HR policy documents
- Accessing dynamic employee information
- Performing calculations
- Invoking tools
- Maintaining conversational context
- Executing multi-step workflows
- Safely performing actions after user confirmation

The architecture should additionally demonstrate how the same agent framework can support broader employee self-service workflows such as onboarding and workplace parking.

---

# 3. Primary Actors

## Employee

Can:

- Ask HR policy questions
- View own leave balance
- Check leave eligibility
- Calculate leave days
- Apply for leave
- Check own leave requests
- Check parking availability
- Reserve parking
- View own parking reservation
- Cancel own parking reservation
- Join parking waitlist

An employee must never be able to access another employee's private information by manipulating chat input.

---

## Manager / HR

Can perform employee capabilities plus authorized onboarding operations:

- Start employee onboarding
- Provide onboarding details
- Create onboarding request
- Create required provisioning tasks
- View onboarding status

Authorization must be enforced by backend code and not solely through prompts.

---

# 4. Workflow Priority

Implementation priority:

1. Leave & Employee HR Assistant
2. Employee Onboarding
3. Parking Assistant

The Leave workflow must be fully functional before moving to secondary workflows.

# 5. Workflow 1 — Employee HR & Leave Assistant

## 5.1 HR Policy Questions

Example:

User:

"What is the casual leave policy?"

Flow:

User
→ Chat API
→ Agent Router
→ Leave/Policy workflow
→ search_hr_policy tool
→ Qdrant retrieval
→ Relevant policy context
→ LLM response
→ Source attribution

Expected behavior:

- Answer must be grounded in retrieved policy content.
- Policy source should be returned when available.
- The model must not invent policy rules when retrieval does not provide sufficient evidence.

---

## 5.2 Leave Balance

Example:

"How many casual leaves do I have?"

Flow:

JWT employee identity
→ get_leave_balance
→ PostgreSQL
→ Response

The employee identifier MUST come from authenticated context.

Never trust an employee ID generated by the LLM for self-service operations.

Example response:

"You currently have 4 Casual Leave days remaining."

---

# 6. Leave Eligibility

Example:

"Can I take casual leave from October 12 to October 16?"

The agent may need to orchestrate:

- get_leave_balance
- get_holidays
- calculate_leave_days
- search_hr_policy
- check_leave_eligibility

Flow:

User request
→ Extract dates and leave type
→ Retrieve balance
→ Retrieve holidays
→ Calculate working days
→ Retrieve relevant policy rules
→ Apply deterministic eligibility rules
→ Generate response

Business calculations must be performed in Python/domain services rather than relying on the LLM to calculate them.

---

# 7. Leave Application

Example:

User:

"Okay, apply it."

The system must use existing conversation context.

Flow:

Previous leave context
→ Validate request
→ Build pending action
→ Display confirmation
→ Wait for explicit user confirmation
→ apply_leave
→ Persist request
→ Return request ID

Example confirmation:

Leave Request

Dates: Oct 12 – Oct 16
Casual Leave: 4 days
Privilege Leave: 1 day

Proceed with submission?

The leave request MUST NOT be created before confirmation.

# 8. Workflow 2 — Employee Onboarding

This workflow demonstrates multi-step agent orchestration.

Example:

"Onboard Priya as a Backend Developer joining October 15."

The agent extracts:

- Employee name
- Designation
- Joining date

It determines required information is missing.

Potential required fields:

- Name
- Email
- Designation
- Department
- Reporting manager
- Joining date
- Location
- Employment type

The agent asks only for missing information.

Example:

"I need the department, reporting manager, work location and employment type."

User:

"Engineering, Karthik, Chennai, Permanent."

The conversation state must merge these values with previously collected values.

---

# 9. Onboarding Validation

Before creating onboarding:

1. Validate caller authorization.
2. Check whether employee already exists.
3. Validate required fields.
4. Retrieve onboarding/access requirements.
5. Generate onboarding plan.
6. Ask for confirmation.
7. Execute provisioning requests.

Example tool:

check_employee_exists

If employee exists, the workflow must not create a duplicate employee.

# 14. Workflow 3 — Workplace Parking Assistant

Parking demonstrates that the same conversational architecture can orchestrate a non-HR employee-service domain.

Example:

"I'm coming to office tomorrow. Can I get parking?"

Flow:

Authenticated employee
→ Resolve requested date
→ Retrieve employee vehicle
→ Check parking availability
→ Offer available slot
→ Request confirmation
→ Reserve parking

---

# 15. Parking Availability

Tools:

- get_employee_vehicle
- check_parking_availability

Example:

"Slot B-24 is available tomorrow for your registered vehicle TN-XX-1234. Would you like me to reserve it?"

Availability must come from PostgreSQL.

The LLM must never invent an available slot.

---

# 16. Parking Reservation

After confirmation:

reserve_parking

Rules:

- Employee must be authenticated.
- Slot must still be available at execution time.
- Employee cannot reserve multiple parking slots for the same date.
- Reservation should be transactional.
- Concurrent requests must not result in duplicate allocation of the same slot.

---

# 17. Parking Cancellation

Example:

"Cancel tomorrow's parking."

Flow:

Resolve authenticated employee
→ Find reservation
→ Show reservation
→ Ask for confirmation
→ cancel_parking
→ Persist cancellation

---

# 18. Parking Waitlist

If parking is full:

"All regular parking slots are currently reserved for tomorrow. Would you like me to add you to the waiting list?"

After confirmation:

join_parking_waitlist

The waitlist should prevent duplicate entries for the same employee/date.

---

# 19. Single Chat Experience

All workflows must operate through one chat endpoint.

Primary endpoint:

POST /api/v1/chat

The frontend must not decide which workflow to invoke.

Example conversation:

User:
"Book parking tomorrow."

Agent:
"Slot B-24 is available. Shall I reserve it?"

User:
"Yes."

Agent:
"Your parking reservation has been confirmed."

User:
"Also, how many casual leaves do I have?"

Agent:
"You have 4 Casual Leave days remaining."

The agent must switch domains naturally while maintaining relevant conversation state.

---

# 20. Agent Routing

Supported routing domains:

- leave
- onboarding
- parking
- policy
- general

Routing should use structured output.

Example conceptual model:

RouteDecision:
- domain
- confidence / metadata if useful

Avoid fragile string matching.

Deterministic shortcuts may be used where appropriate, but routing should support natural-language variations.

---

# 21. Conversation State

Conversation state should contain at minimum:

- messages
- user_id
- employee_id
- role
- active_domain
- leave_context
- onboarding_context
- parking_context
- pending_action

Pending actions must survive the request/response boundary so that:

User:
"Reserve B-24 tomorrow."

Agent:
"Please confirm."

User:
"Confirm."

correctly executes the previously prepared action.

---

# 22. Authentication

Use JWT authentication.

JWT should contain or resolve:

- user_id
- employee_id
- role

The API layer validates JWT and creates trusted user context.

Agent/tool code must use trusted authenticated context for authorization-sensitive operations.

Never allow the LLM to override authenticated employee identity.

---

# 23. Authorization

Example permissions:

EMPLOYEE:
- Policy questions
- Own leave balance
- Own leave applications
- Own parking reservations

MANAGER / HR:
- Employee capabilities
- Employee onboarding operations

Authorization MUST be enforced within application/domain services.

Prompt instructions are not considered security controls.

---

# 24. Human-in-the-Loop Rules

Read-only operations do not require confirmation.

Examples:

- search_hr_policy
- get_leave_balance
- get_holidays
- check_parking_availability
- get_onboarding_status

State-changing operations require confirmation.

Examples:

- apply_leave
- create_employee/onboarding
- create_access_request
- reserve_parking
- cancel_parking
- join_parking_waitlist

Pattern:

Agent proposes action
→ Store PendingAction
→ Ask user for confirmation
→ User confirms
→ Revalidate
→ Execute
→ Clear PendingAction

Never execute a write merely because the LLM says it should.

---

# 25. RAG Requirements

HR policy documents are indexed into Qdrant.

Pipeline:

PDF
→ Document loader
→ Text cleaning
→ Chunking
→ Embeddings
→ Qdrant

Recommended embedding model:

BAAI/bge-small-en-v1.5

Each chunk should retain metadata where possible:

- document
- section
- page
- category

Runtime:

Question
→ Query embedding
→ Qdrant similarity search
→ Top-K context
→ Context construction
→ LLM
→ Grounded answer + source

---

# 26. Data Ownership

Use Qdrant for knowledge:

- HR policies
- Leave policies
- Onboarding policies
- Static organizational knowledge

Use PostgreSQL for transactional/live information:

- Employees
- Users
- Leave balances
- Leave requests
- Holidays
- Onboarding requests
- Onboarding tasks
- Vehicles
- Parking slots
- Parking reservations
- Parking waitlist
- Conversation/checkpoint information where applicable

Never use vector search as the source of truth for transactional state.

# 28. Business Logic

Business rules should live in domain/application services.

Examples:

LeaveEligibilityService:
- calculate working days
- exclude holidays
- validate balance
- enforce leave rules

ParkingService:
- check availability
- prevent duplicate reservations
- reserve slot atomically
- cancel reservation
- waitlist employee

OnboardingService:
- validate required fields
- check duplicate employee
- determine provisioning requirements
- create onboarding tasks
- calculate onboarding status

# 29. Error Handling

The system must gracefully handle:

- Invalid authentication
- Unauthorized operations
- Missing employee record
- Missing leave balance
- Invalid dates
- Insufficient leave
- Policy retrieval failure
- Duplicate onboarding
- Missing onboarding fields
- Parking unavailable
- Duplicate parking reservation
- Concurrent parking booking conflict
- Database failure
- LLM provider failure
- Vector database failure

Return user-friendly messages while logging technical details.

# 38. Core Design Principle

The application should clearly separate:

LLM responsibilities:
- Natural-language understanding
- Intent classification
- Structured information extraction
- Tool selection
- Natural-language response generation

Application responsibilities:
- Authentication
- Authorization
- Business rules
- Calculations
- Validation
- Transactions
- Persistence
- Side-effect control

RAG responsibilities:
- Retrieve relevant organizational knowledge
- Ground policy answers
- Provide source metadata

The LLM is an orchestrator and language interface, not the system of record.
